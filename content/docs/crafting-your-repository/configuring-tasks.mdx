작업은 Turborepo가 실행하는 스크립트입니다. [`turbo.json` configuration](/docs/reference/configuration)과 [Package Graph](/docs/core-concepts/package-and-task-graph#package-graph)에서 작업 간의 관계를 표현할 수 있습니다.

Turborepo는 가능한 모든 작업을 항상 병렬화해 전체 실행 속도가 최대한 빨라지도록 합니다. 이는 작업을 하나씩 차례대로 실행하는 것보다 빠르며, Turborepo가 매우 빠른 이유 중 하나입니다.

예를 들어 `yarn workspaces run lint && yarn workspaces run build && yarn workspaces run test`는 다음처럼 보일 것입니다.

![스크립트가 실행되지 않는 빈 공간이 많이 남아 있는 상태로, 작업이 순차적으로 실행되는 모습을 그래픽으로 표현한 이미지입니다.](/images/docs/slow-tasks-light.png)

하지만 Turborepo로 같은 작업을 **더 빠르게** 처리하려면 `turbo run lint build test`를 사용할 수 있습니다.

![`turbo run lint test build`를 그래픽으로 표현한 이미지입니다. 모든 작업이 병렬로 실행되며, 스크립트가 실행되지 않는 빈 공간이 훨씬 적습니다.](/images/docs/turborepo-tasks-fast-light.png)

## 시작하기

루트 `turbo.json` 파일은 Turborepo가 실행할 작업을 등록하는 곳입니다. 작업을 정의하고 나면 [`turbo run`](/docs/reference/run)을 사용해 하나 이상의 작업을 실행할 수 있습니다.

- 새로 시작하는 경우에는 [`create-turbo`를 사용해 새 저장소를 만들고](/docs/getting-started/installation), `turbo.json` 파일을 편집하면서 이 가이드의 예제를 직접 시도해 보기를 권장합니다.
- 기존 저장소에 Turborepo를 도입하는 경우 저장소 루트에 `turbo.json` 파일을 만드세요. 이 가이드의 나머지 구성 옵션도 이 파일을 바탕으로 살펴보게 됩니다.

## 작업 정의하기

`tasks` 객체의 각 키는 `turbo run`으로 실행할 수 있는 작업입니다. Turborepo는 **각 패키지의 `package.json`에서 작업 이름과 같은 이름의 스크립트**를 찾습니다.

작업을 정의하려면 `turbo.json`의 [`tasks` object](/docs/reference/configuration#tasks)를 사용하세요. 예를 들어 의존성도 없고 출력도 없는 `build`라는 기본 작업은 다음처럼 보일 수 있습니다.

```json title="./turbo.json"
{
  "tasks": {
    "build": {} // 잘못된 예시입니다! // [!code highlight]
  }
}
```

이 시점에서 `turbo run build`를 실행하면 Turborepo는 패키지들의 모든 `build` 스크립트를 병렬로 실행하고, 어떤 파일 출력도 캐시하지 않습니다. **이 상태는 곧바로 오류로 이어질 수 있습니다.** 기대한 방식으로 동작하게 만들려면 몇 가지 중요한 요소가 아직 빠져 있습니다.

### 올바른 순서로 작업 실행하기

[The `dependsOn` key](/docs/reference/configuration#dependson)는 다른 작업이 시작되기 전에 먼저 완료되어야 하는 작업을 지정하는 데 사용됩니다. 예를 들어 대부분의 경우, 애플리케이션의 `build` 스크립트가 실행되기 전에 라이브러리의 `build` 스크립트가 완료되기를 원할 것입니다. 이를 위해 다음과 같은 `turbo.json`을 사용할 수 있습니다.

```json title="./turbo.json"
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"] // [!code highlight]
    }
  }
}
```

이제 기대한 빌드 순서, 즉 _의존 대상_을 먼저 빌드하고 _의존하는 쪽_을 나중에 빌드하는 흐름이 만들어졌습니다.

**하지만 주의하세요.** 아직 이 빌드 결과를 캐시 대상으로 표시하지 않았습니다. 이를 위해서는 [Specifying outputs](#specifying-outputs) 섹션으로 이동하세요.

#### `^`로 의존 패키지의 작업에 의존하기

`^` 마이크로 문법은 Turborepo에게 대상 패키지보다 먼저 직접 의존 패키지에서 해당 작업을 실행하라고 지시합니다. 애플리케이션이 `ui`라는 라이브러리에 의존하고 있고 그 라이브러리에 `build` 작업이 있다면, `ui`의 `build` 스크립트가 **먼저** 실행됩니다. 그리고 그것이 성공적으로 끝난 후에 애플리케이션의 `build` 작업이 실행됩니다.

이는 애플리케이션의 `build` 작업이 컴파일에 필요한 모든 의존성을 확보한 상태에서 실행되도록 보장하는 중요한 패턴입니다. 이 개념은 의존성 그래프가 더 복잡해져 여러 단계의 작업 의존성을 포함하게 될 때도 그대로 적용됩니다.

#### 같은 패키지 안의 작업에 의존하기

때로는 같은 패키지 안의 두 작업이 특정 순서로 실행되어야 할 수도 있습니다. 예를 들어 같은 라이브러리에서 `test` 작업을 실행하기 전에 `build` 작업을 먼저 실행해야 할 수 있습니다. 이 경우에는 `dependsOn` 키에 해당 스크립트를 일반 문자열로 지정하면 됩니다. (`^`는 붙이지 않습니다.)

```json title="./turbo.json"
{
  "tasks": {
    "test": {
      "dependsOn": ["build"] // [!code highlight]
    }
  }
}
```

#### 특정 패키지의 특정 작업에 의존하기

특정 패키지의 개별 작업 하나를 의존 대상으로 지정할 수도 있습니다. 아래 예시에서는 `utils`의 `build` 작업이 어떤 `lint` 작업보다 먼저 실행되어야 합니다.

```json title="./turbo.json"
{
  "tasks": {
    "lint": {
      "dependsOn": ["utils#build"] // [!code highlight]
    }
  }
}
```

의존 작업을 더 구체적으로 지정해서 특정 패키지에만 적용할 수도 있습니다.

```json title="./turbo.json"
{
  "tasks": {
    "web#lint": {
      "dependsOn": ["utils#build"] // [!code highlight]
    }
  }
}
```

이 구성을 사용하면 `web` 패키지의 `lint` 작업은 `utils` 패키지의 `build` 작업이 완료된 뒤에만 실행될 수 있습니다.

#### 의존성이 없는 경우

어떤 작업들은 다른 작업에 의존하지 않을 수도 있습니다. 예를 들어 Markdown 파일의 오타를 찾는 작업은 다른 작업의 상태를 신경 쓸 필요가 없을 가능성이 큽니다. 이 경우 `dependsOn` 키를 생략하거나 빈 배열을 제공하면 됩니다.

```json title="./turbo.json"
{
  "tasks": {
    "spell-check": {
      "dependsOn": [] // [!code highlight]
    }
  }
}
```

### `outputs` 지정하기

<Callout type="info">
  Turborepo는 같은 작업을 두 번 하지 않도록 작업의 출력을 캐시합니다.
  자세한 내용은 [Caching
  guide](/docs/crafting-your-repository/caching)에서 다루겠지만, 우선은
  작업이 올바르게 구성되어 있는지부터 확인해 봅시다.
</Callout>

`outputs` 키는 작업이 성공적으로 완료됐을 때 Turborepo가 캐시해야 할 **파일과 디렉터리**를 알려줍니다. **이 키가 정의되어 있지 않으면 Turborepo는 어떤 파일도 캐시하지 않습니다. 이후 실행에서 캐시 적중이 발생해도 파일 출력은 복원되지 않습니다.**

아래는 자주 쓰이는 도구들의 출력 예시 몇 가지입니다.

<Tabs items={["Next.js", "Vite", "tsc"]} storageKey="outputs-tools">
<Tab value="Next.js">
```json title="./turbo.json"
{
  "tasks": {
    "build": {
      "outputs": [".next/**", "!.next/cache/**"] // [!code highlight]
    }
  }
}
```
</Tab>

<Tab value="Vite">
```json title="./turbo.json"
{
  "tasks": {
    "build": {
      "outputs": ["dist/**"] // [!code highlight]
    }
  }
}
```
</Tab>
<Tab value="tsc">
```json title="./turbo.json"
{
  "tasks": {
    "build": {
      "outputs": ["dist/**"] // [!code highlight]
    }
  }
}
```
</Tab>
</Tabs>

Glob 패턴은 패키지 기준의 상대 경로이므로 `dist/**`는 각 패키지에서 생성되는 `dist`를 각각 처리합니다. `outputs` 키에 사용할 glob 패턴을 만드는 방법은 [glob 사양](/docs/reference/globs)을 참고하세요.

### `inputs` 지정하기

`inputs` 키는 [캐싱](/docs/crafting-your-repository/caching)을 위해 작업 해시에 포함하고 싶은 파일을 지정하는 데 사용됩니다. 기본적으로 Turborepo는 Git에서 추적 중인 패키지의 모든 파일을 포함합니다. 하지만 `inputs` 키를 사용하면 해시에 포함될 파일을 더 구체적으로 제어할 수 있습니다.

예를 들어 Markdown 파일의 오타를 찾는 작업은 다음과 같이 정의할 수 있습니다.

```json title="./turbo.json"
{
  "tasks": {
    "spell-check": {
      "inputs": ["**/*.md", "**/*.mdx"] // [!code highlight]
    }
  }
}
```

이제 Markdown 파일이 바뀌었을 때만 `spell-check` 작업에서 캐시 누락이 발생합니다.

<Callout type="error">
이 기능을 사용하면 소스 제어에서 추적하는 변경 사항을 따라가는 것을 포함해 Turborepo의 기본 `inputs` 동작이 모두 비활성화됩니다. 즉, `.gitignore` 파일이 더 이상 적용되지 않으므로, glob 패턴으로 해당 파일들을 포함하지 않도록 직접 보장해야 합니다.

기본 동작을 복원하려면 [`$TURBO_DEFAULT$` 마이크로 문법](#restoring-defaults-with-turbo_default)을 사용하세요.

</Callout>

#### `$TURBO_DEFAULT$`로 기본값 복원하기

[The default `inputs` behavior](/docs/reference/configuration#inputs)는 많은 작업에서 그대로 원하는 동작일 것입니다. 하지만 작업 출력에 영향을 주지 않는다고 알려진 파일 변경을 무시하도록 `inputs`를 세밀하게 조정하면 특정 작업의 캐시 적중률을 더 높일 수 있습니다.

이 때문에 `$TURBO_DEFAULT$` 마이크로 문법을 사용해 기본 `inputs` 동작을 미세 조정할 수 있습니다.

```json title="./turbo.json"
{
  "tasks": {
    "build": {
      "inputs": ["$TURBO_DEFAULT$", "!README.md"] // [!code highlight]
    }
  }
}
```

이 작업 정의에서 Turborepo는 `build` 작업에 대해 기본 `inputs` 동작을 사용하지만 `README.md` 파일 변경은 무시합니다. `README.md`가 바뀌어도 이 작업은 계속 캐시에 적중합니다.

### 루트 작업 등록하기

`turbo`를 사용해 Workspace 루트의 `package.json`에 있는 스크립트도 실행할 수 있습니다. 예를 들어 각 패키지의 `lint` 작업과 함께, Workspace 루트 디렉터리의 파일을 대상으로 `lint:root` 작업을 실행하고 싶을 수 있습니다.

<Tabs items={["turbo.json", "package.json"]}>
<Tab value="turbo.json">
```json title="./turbo.json"
{
  "tasks": {
    "lint": {
      "dependsOn": ["^lint"]
    },
    "//#lint:root": {} // [!code highlight]
  }
}
```

</Tab>
<Tab value="package.json">
```json title="./package.json"
{
  "scripts": {
    "lint": "turbo run lint lint:root",
    "lint:root": "eslint ." // [!code highlight]
  }
}
```
</Tab>
</Tabs>

루트 작업을 등록하고 나면 루트에서 `turbo run lint:root`를 실행하거나, 어느 워크스페이스에서든 `turbo run //#lint:root`를 실행해 이 작업을 수행할 수 있습니다. `turbo run lint lint:root`를 실행해 모든 린팅 작업을 함께 돌리는 것도 가능합니다.

#### 언제 루트 작업을 써야 하나요?

- **Workspace 루트 린팅 및 포매팅**: Workspace 루트에 있는 코드도 린트하거나 포맷하고 싶을 수 있습니다. 예를 들어 루트 디렉터리에서 ESLint나 Prettier를 실행하고 싶을 수 있습니다.
- **점진적 마이그레이션**: Turborepo로 마이그레이션하는 동안 아직 패키지로 옮기지 않은 스크립트가 일부 남아 있을 수 있습니다. 이 경우 루트 작업을 만들어 먼저 마이그레이션을 시작하고, 나중에 작업을 패키지로 분산시킬 수 있습니다.
- **패키지 범위가 없는 스크립트**: 특정 패키지 맥락에서는 의미가 없지만 여전히 실행해야 하는 스크립트가 있을 수 있습니다. 이런 스크립트는 루트 작업으로 등록해 `turbo`의 캐싱, 병렬화, 워크플로 기능을 계속 활용할 수 있습니다.

## 고급 사용 사례

### Package Configurations 사용하기

[Package Configurations](/docs/reference/package-configurations)은 패키지 안에 직접 배치하는 `turbo.json` 파일입니다. 이를 통해 하나의 패키지가 저장소 전체에 영향을 주지 않고, 자기 작업에 대한 특정 동작만 별도로 정의할 수 있습니다.

많은 팀이 함께 작업하는 대규모 모노레포에서는 이를 통해 각 팀이 자신의 작업을 더 잘 제어할 수 있습니다. 자세한 내용은 [패키지 구성 문서](/docs/reference/package-configurations)를 참고하세요.

### 구성 조합하기

[Package Configurations](/docs/reference/package-configurations)은 더 적은 구성으로 더 많은 제어를 얻을 수 있도록 조합해서 사용할 수 있습니다.

- [**다른 패키지로부터 확장하기**](/docs/reference/package-configurations#extending-from-other-packages): 여러 패키지가 확장할 수 있는 공유 구성 패키지를 만들어, `turbo.json` 구성을 공통으로 재사용할 수 있습니다.
- [**확장된 구성에 값 추가하기**](/docs/reference/package-configurations#extending-arrays-with-turbo_extends): 상속받은 `outputs`, `env` 같은 배열 값을 완전히 덮어쓰는 대신, `$TURBO_EXTENDS$` 마이크로 문법으로 값만 추가할 수 있습니다.

### 런타임 의존성이 있는 장기 실행 작업

항상 다른 작업과 함께 실행돼야 하는 장기 실행 작업이 있을 수 있습니다. 이때는 [`with` 키](/docs/reference/configuration#with)를 사용하세요.

```json title="./apps/web/turbo.json"
{
  "tasks": {
    "dev": {
      "with": ["api#dev"],
      "persistent": true,
      "cache": false
    }
  }
}
```

장기 실행 작업은 종료되지 않기 때문에 여기에 직접 의존할 수 없습니다. 대신 `with` 키워드는 `web#dev` 작업이 실행될 때마다 `api#dev` 작업도 함께 실행합니다.

### 부작용이 있는 작업 수행하기

캐시된 빌드 뒤의 배포 스크립트처럼, 어떤 상황에서도 항상 실행되어야 하는 작업이 있습니다. 이런 작업에는 작업 정의에 `"cache": false`를 추가하세요.

```json title="./turbo.json"
{
  "tasks": {
    "deploy": {
      "dependsOn": ["^build"],
      "cache": false // [!code highlight]
    },
    "build": {
      "outputs": ["dist/**"]
    }
  }
}
```

### 의존성이 있지만 병렬로 실행할 수 있는 작업

일부 작업은 다른 패키지에 의존하고 있더라도 병렬로 실행할 수 있습니다. 대표적인 예가 타입 체커입니다. 타입 체커는 의존 패키지의 출력이 실제로 생성될 때까지 기다리지 않아도 올바르게 동작할 수 있기 때문입니다.

이 때문에 `check-types` 작업을 아래처럼 정의하고 싶어질 수 있습니다.

```json title="./turbo.json"
{
  "tasks": {
    "check-types": {} // 잘못된 예시입니다! // [!code highlight]
  }
}
```

이렇게 하면 작업이 병렬로 실행되지만, 의존성의 소스 코드 변경은 반영되지 않습니다. 즉, 다음과 같은 일이 가능해집니다.

1. `ui` 패키지의 인터페이스를 깨뜨리는 변경을 합니다.
2. `turbo check-types`를 실행했는데, `ui`에 의존하는 애플리케이션 패키지에서 캐시 적중이 발생합니다.

이것은 잘못된 결과입니다. 애플리케이션 패키지가 새 인터페이스를 사용하도록 업데이트되지 않았는데도 성공적인 캐시 적중으로 표시되기 때문입니다. 이 상태에서 편집기에서 TypeScript 오류를 직접 확인해 보면 실제 오류가 드러날 가능성이 높습니다.

그래서 `check-types` 작업 정의를 약간 바꾸게 됩니다.

```json title="./turbo.json"
{
  "tasks": {
    "check-types": {
      "dependsOn": ["^check-types"] // 동작은 하지만... 더 빠를 수 있습니다! // [!code highlight]
    }
  }
}
```

이제 다시 `ui` 패키지에 깨지는 변경을 넣고 테스트해 보면, 캐싱 동작은 올바르게 바뀐 것을 볼 수 있습니다. 하지만 작업은 더 이상 병렬로 실행되지 않습니다.

이 두 가지 요구사항(정확성, 병렬성)을 모두 만족시키기 위해, 작업 그래프에 [Transit Nodes](/docs/core-concepts/package-and-task-graph#transit-nodes)를 도입할 수 있습니다.

```json title="./turbo.json"
{
  "tasks": {
    "transit": {
      "dependsOn": ["^transit"]
    },
    "check-types": {
      "dependsOn": ["transit"]
    }
  }
}
```

이 Transit Node는 어떤 `package.json`의 스크립트와도 일치하지 않아 실제로는 아무 작업도 하지 않는 작업이지만, 이를 통해 패키지 의존성 사이의 관계를 표현할 수 있습니다. 그 결과 작업은 병렬로 실행되면서도, 내부 의존성의 변경 사항을 인식할 수 있게 됩니다.

<Callout type="info">
  이 예시에서는 `transit`이라는 이름을 사용했지만, Workspace에 이미 존재하는
  스크립트 이름만 아니라면 어떤 이름이든 사용할 수 있습니다.
</Callout>
