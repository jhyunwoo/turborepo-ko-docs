Turborepo는 지속적인 통합 파이프라인에서 수행해야 하는 빌드, 린트, 테스트 및 기타 작업 속도를 높입니다. 병렬화 및 [원격 캐싱](/docs/core-concepts/remote-caching)을 통해 Turborepo는 CI를 훨씬 더 빠르게 만듭니다.

CI 공급업체를 원격 캐시에 연결하고 작업을 실행하는 방법에 대한 예를 보려면 [CI 가이드](/docs/guides/ci-vendors)를 방문하세요.

## 원격 캐싱 활성화

CI에 원격 캐싱을 활성화하려면 Turborepo에 대한 환경 변수를 설정하여 원격 캐시에 액세스하세요.

| 환경 변수 | 설명 |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TURBO_TOKEN` | 원격 캐시에 액세스하기 위한 Bearer 토큰 |
| `TURBO_TEAM` | 저장소와 연결된 계정 이름입니다. [Vercel 원격 캐시](https://vercel.com/docs/monorepos/remote-caching)를 사용하는 경우, 이것이 [팀의 슬러그](https://vercel.com/docs/accounts/create-a-team#find-your-team-id)입니다. |

`turbo`을 통해 작업을 실행하면 CI가 캐시에 도달하여 파이프라인 속도를 높일 수 있습니다.

<Callout type="info" title="원격 캐시 호스팅">
Vercel의 내장 CI/CD는 구성 없이 관리되는 Vercel 원격 캐시에 자동으로 연결됩니다. 다른 CI 공급업체를 Vercel 원격 캐시에 연결하기 위한 토큰을 검색하려면 [Vercel 원격 캐시 설명서](https://vercel.com/docs/monorepos/remote-caching#use-remote-caching-from-external-ci/cd)를 방문하세요.

자체 호스팅 원격 캐시 옵션을 보려면 [Turborepo의 원격 캐시 설명서](/docs/core-concepts/remote-caching#remote-cache-api)를 방문하세요.

</Callout>

## CI에서 작업 실행

개발 및 CI 머신에 [`turbo` 전역 설치](/docs/getting-started/installation#global-installation)를 통해 하나의 정신 모델을 사용하여 개발부터 출시까지 전체 저장소를 실행할 수 있습니다. `turbo.json`에 등록한 작업은 CI에서도 동일하게 작동합니다.

- 작업 설정 방법에 대한 자세한 내용은 [작업 구성](/docs/crafting-your-repository/configuring-tasks) 페이지를 참조하세요.
- CI에서 작업을 실행하는 예는 [CI 가이드](/docs/guides/ci-vendors)를 참조하세요.

### 진입점 필터링

`turbo` 로컬로 작업할 때와 정확히 동일하게 [`--filter` 플래그](/docs/reference/run#--filter-string)를 사용하여 작업을 필터링할 수 있습니다. CI에서는 패키지, 디렉터리, Git 기록별 필터링이 모두 지원됩니다.

<Callout type="info" title="CI에서 Git 기록 사용">
  소스 제어 변경을 사용한 필터링은 기록이 있는 경우에만 가능합니다.
 기계에서 사용 가능합니다. 얕은 클론을 사용하는 경우 기록이 생성되지 않습니다.
 가능합니다.
</Callout>

[`--affected` 플래그](#running-only-affected-tasks)를 사용하여 변경 사항이 있는 패키지의 작업만 실행할 수도 있습니다.

## 도커

Docker는 많은 배포 파이프라인에서 중요한 부분입니다. [Turborepo의 `prune` 하위 명령](/docs/reference/prune)은 이미지에서 불필요한 종속성과 코드를 제거하여 경량 이미지를 제공하는 데 도움이 됩니다.

Docker를 사용하여 Turborepo에서 배포하는 방법에 대한 자세한 내용은 [전용 Docker 가이드](/docs/guides/tools/docker)를 참조하세요.

## 작업 및 기타 불필요한 작업 건너뛰기

### 영향을 받는 작업만 실행

`--affected` 플래그를 사용하면 변경 사항이 있는 작업만 실행할 수 있습니다.

```bash title="Terminal"
turbo run build --affected
```

다음과 같은 상황에서 이 플래그를 사용하는 것이 좋습니다.

- 모노레포의 여러 패키지에서 많은 작업을 실행하고 있으며 코드가 변경된 패키지에서만 해당 작업을 실행하려고 합니다.
- 원격 캐시를 사용하지 _않지만_ CI에서 가능한 한 적은 작업을 수행하고 싶습니다.
- 귀하는 원격 캐시를 사용하고 있으며, 대규모 저장소에 있습니다. 캐시에서 복원되는 작업의 양을 최소화하면 네트워크를 통해 전송할 데이터가 줄어들어 캐시 복원 속도가 빨라집니다.
- 이미 [고급 필터링 기술](/docs/reference/run#advanced-filtering-examples) 또는 [`turbo-ignore`](/docs/reference/turbo-ignore)을 사용하여 `--affected`과 동일하거나 유사한 동작을 생성하고 있습니다. 이 새로운 플래그를 사용하여 스크립팅을 단순화할 수 있는 기회가 있을 것입니다.
 - `--affected`은 모든 작업 실행으로 돌아가기 때문에 맞춤형 필터링보다 얕은 복제를 더 원활하게 처리할 수 있습니다.

#### GitHub Actions에서 `--affected` 사용

CI/CD 파이프라인은 `--affected`을 사용하기에 완벽한 장소입니다. `--affected`을 사용하면 Turborepo는 `GITHUB_BASE_REF`과 같이 GitHub에서 설정한 환경 변수를 검사하여 GitHub Actions에서 실행 중인지 자동으로 감지할 수 있습니다.

PR의 맥락에서 이는 Turborepo가 ​​PR의 기본 분기와 PR의 헤드 분기 사이에서 변경된 패키지를 확인할 수 있음을 의미합니다. 이를 통해 PR 변경 사항의 영향을 받는 패키지에 대해서만 작업을 실행할 수 있습니다.

`GITHUB_BASE_REF`은 `pull_request` 및 `pull_request_target` 이벤트에서 잘 작동하지만 일반 푸시 이벤트 중에는 사용할 수 없습니다. 이러한 경우 `GITHUB_EVENT_PATH`을 사용하여 커밋을 비교할 기본 브랜치를 결정합니다. 추가 커밋 없이 분기를 강제로 푸시하고 푸시하는 경우 분기의 ​​첫 번째 커밋의 상위 항목과 비교합니다.

### `turbo-ignore` 사용

코드베이스와 CI가 성장함에 따라 더 빠르게 속도를 높일 수 있는 더 많은 방법을 찾기 시작할 수도 있습니다. 캐시를 사용하는 것이 유용하지만 작업을 완전히 건너뛸 수도 있습니다. `turbo-ignore`을 사용하면 어쨌든 캐시 적중을 초래하는 종속성 설치와 같은 긴 컨테이너 준비 단계를 건너뛸 수 있습니다.

## 모범 사례

### 캐싱에 의존

Turborepo의 캐싱 기능을 사용하면 복잡성을 최소화하면서 빠른 CI 파이프라인을 생성할 수 있습니다. [원격 캐싱](/docs/core-concepts/remote-caching)을 통해 `--filter` 플래그를 사용하여 빌드용 패키지를 대상으로 하는 Turborepo는 오버헤드가 거의 없이 대규모 단일 저장소에 대한 변경 감지를 처리합니다.

예를 들어 CI는 다음 두 명령을 실행하여 품질 검사를 신속하게 처리하고 대상 애플리케이션을 구축할 수 있습니다.

- `turbo run lint check-types test`: 전체 저장소에 대한 품질 검사를 실행합니다. 변경되지 않은 모든 패키지는 캐시에 적중됩니다.
- `turbo build --filter=web`: `turbo.json`에 등록한 `build` 작업을 사용하여 `web` 패키지를 빌드합니다. `web` 패키지 또는 해당 종속성이 변경되지 않은 경우 빌드도 캐시에 적중됩니다.

코드베이스가 확장됨에 따라 CI를 최적화할 수 있는 보다 구체적인 기회를 찾을 수 있지만 캐싱에 의존하는 것이 시작하기에 좋은 곳입니다.

### CI의 글로벌 `turbo`

전역 `turbo`을 사용하면 CI 워크플로에서 편리하므로 CI 관련 명령을 쉽게 실행하고 [자동 작업 공간 범위 지정](/docs/crafting-your-repository/running-tasks#automatic-package-scoping)을 활용할 수 있습니다.

그러나 어떤 경우에는 **패키지 관리자로 패키지를 설치하기 전에** `turbo`을 사용하는 `turbo` 명령이나 스크립트를 실행할 수 있습니다. 이에 대한 한 가지 예는 [`turbo prune`을 사용하여 Docker 이미지 생성](/docs/guides/tools/docker#example)입니다. 이 상황에서는 해당 버전의 바이너리가 아직 설치되지 않았기 때문에 전역 `turbo`은 `package.json`의 버전을 사용할 수 없습니다.

이러한 이유로 **CI의 `turbo` 전역 설치를 `package.json`**의 주요 버전에 고정하는 것이 좋습니다. 주요 버전 내에서는 주요 변경 사항이 도입되지 않기 때문입니다. 정확한 버전을 고정하여 안정성을 강화하고 유지 관리 부담을 줄여 패치 릴리스에서 버그 수정을 받을 수도 있습니다.

### CI에 `turbo run` 사용

`turbo run`은 Turborepo에서 작업할 때 사용하는 가장 일반적인 명령이므로 편의상 `turbo`로 별칭이 지정됩니다. 이는 로컬 작업에 적합하지만 [`turbo prune`](/docs/reference/prune) 및 [`turbo generate`](/docs/reference/generate)와 같은 `turbo`에 대한 다른 하위 명령이 있습니다.

우리는 `turbo`을 더 좋게 만들기 위해 항상 노력하고 있으므로 앞으로 더 많은 하위 명령을 추가할 수 있습니다. 이러한 이유로 CI에 `turbo run`을 사용하면 이름 충돌을 방지할 수 있습니다.예를 들어 CI 파이프라인에 `turbo deploy` 명령이 있는 경우 `turbo` CLI에 직접 내장된 잠재적인 `deploy` 하위 명령과 충돌할 수 있습니다. 이를 방지하려면 대신 CI 파이프라인에서 `turbo run deploy`을 사용하세요.

## 문제 해결

### 캐시에 도달하면 빌드가 손상됩니다.

작업이 **캐시를 놓쳤을 때 통과했지만 캐시에 도달했을 때 실패**한다면 작업에 대해 [`outputs` 키](/docs/reference/configuration#outputs)를 올바르게 구성하지 않았을 가능성이 높습니다.

### 잘못된 환경 변수를 사용한 배포

작업에 대해 `env` 또는 `globalEnv` 키를 정의하지 않은 경우 Turborepo는 해시를 생성할 때 해당 키를 사용할 수 없습니다. 이는 다른 환경에 있음에도 불구하고 작업이 캐시에 적중할 수 있음을 의미합니다.

`env` 및 `globalEnv` 키 구성을 확인하세요.
